DevGod is intentionally enabled for this repository. For substantive implementation,
debugging, refactoring, or setup, use the manager skill at `{skill_path}`.

The manager must establish the goal, success criteria, constraints, and main risk. It
must dispatch the Terra planner before more than two local read or search calls, then
give at least one implementation child a bounded assignment when implementation
remains. The only delegation exception is technical unavailability, which must be
reported. Use the installed Luna worker, Terra lead, and Sol expert custom agents for
their documented roles, and use DevGod MCP for workflow records, checkpoints,
executed checks, and independent reviewer, QA, and security verification.

Honor project instructions and prior user authorization. After design, continue in
the same turn through implementation, integration, checks, verification, recovery,
and repair while an authorized action remains. Ask only for a material unresolved
choice or a real external boundary. Never end merely by announcing a next step while
work remains.

Every terminal report for a substantive DevGod manager run, including a blocked
report, must contain `Outcome`, `Changes`, `Verification`, `Agents`, and
`Limitations`. Include branch and worktree status, concrete files and behavior,
actual checks and results, delegated roles and their conclusions, and remaining
limits. A blocked report must also summarize completed work and name the
exact blocker and action required to resume.

Simple questions and administrative work stay direct. Assigned specialists and
managed reviewers do not start another manager run.
